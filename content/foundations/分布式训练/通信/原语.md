# 分布式训练中的通信原语：从 Send/Recv 到 AllReduce

> 单张 GPU 上，训练的主角是矩阵乘法；跨越多张 GPU 后，系统还必须不断搬运参数、梯度、激活和 token。**通信原语（communication primitive）定义了这些数据从哪里来、到哪里去，以及是否需要在途中完成求和等归约。**

如果只记住一句话：

> **先看通信前后的数据布局，再选原语：邻居之间传数据用 Send/Recv；一份数据复制给所有 rank 用 Broadcast；每份数据求和且所有 rank 都要结果用 AllReduce；从分片恢复完整张量用 AllGather；求和后仍只保留分片用 ReduceScatter；把不同数据路由给不同 rank 用 AllToAll。**

本文以 4 个 rank 为例，从语义、数据布局和通信成本讲清常见原语，再说明它们如何组成 DDP、张量并行、流水线并行、FSDP/ZeRO 和 MoE。

读完本文，你应该能回答五个问题：

1. AllGather、ReduceScatter 和 AllReduce 到底分别改变了什么？
2. 为什么 AllReduce 可以分解为 ReduceScatter + AllGather？
3. 为什么 DDP、FSDP、Pipeline Parallel 和 MoE 使用的原语不同？
4. “传输字节数相同”为什么不代表“通信时间相同”？
5. 一个 collective 卡住时，应该先检查哪些地方？

---

## 1. 先建立心智模型：原语描述结果，算法描述过程

通信领域有三个容易混在一起的层次：

| 层次 | 回答的问题 | 例子 |
|---|---|---|
| 通信原语 | 通信结束后，每个 rank 应该拥有什么数据？ | AllReduce、AllGather、AllToAll |
| 通信算法 | 数据沿什么路径、分几轮传输？ | Ring、Tree、Recursive Doubling、分层算法 |
| 通信后端 | 谁负责建立连接、选择算法并执行传输？ | NCCL、Gloo、MPI、CCL |

例如，“所有 rank 最终都得到梯度之和”是 **AllReduce 的语义**。这个 AllReduce 可以由 Ring 实现，也可以由 Tree 或分层算法实现。调用方通常只声明想要的结果，通信库再根据消息大小、GPU 拓扑和网络选择具体算法。

所以：

- **AllReduce 不是 Ring AllReduce 的同义词；**
- “AllReduce = Reduce + Broadcast”或“AllReduce = ReduceScatter + AllGather”首先是语义上的等价关系；
- 底层不一定真的依次调用这些高层 API。

后文先讲稳定的**语义**，再单独讨论会随实现与硬件变化的**性能**。

### 1.1 rank、world size 与 process group

分布式框架通常把参与通信的进程或设备编号为 `rank`。使用 subgroup 时，还要区分全局编号与组内编号：

| 名词 | 含义 |
|---|---|
| global rank | 进程在默认 WORLD group 中的全局编号 |
| group-local rank | 进程在某个 subgroup 中的位置，可能与 global rank 不同 |
| world size / group size | 默认 WORLD group / 当前 subgroup 中的参与者数量 |
| process group / communicator | 哪些 rank 共同参与一组通信 |

假设本文中的通信组包含 4 个 rank：

```text
Process Group = {R0, R1, R2, R3}
world size p  = 4
```

本文图中的 `R0`～`R3` 统一表示**组内逻辑参与者**，$p$ 表示当前 collective 所在 group 的大小。在混合并行中，一个进程可能同时属于 DP、TP、PP 和 EP 等多个 group；具体 API 接收 global rank 还是 group-local rank，要以框架文档为准。

### 1.2 本文的表示方法

后文使用：

- `R0`～`R3` 表示 4 个 rank；
- `[A | B | C | D]` 表示一个张量被切成 4 个连续分片；
- $\oplus$ 表示归约运算，可以是 `SUM`、`MAX`、`MIN` 等；
- 若没有特别说明，例子中的归约均为逐元素求和。

通信原语不关心 `A` 是参数、梯度、激活还是 token。**同一种数据布局变化，可以服务于完全不同的训练策略。**

### 1.3 Collective 是一份组内契约

集合通信（collective communication）要求组内相关 rank 共同参与。通常必须保证：

- 使用同一个 process group；
- 以兼容的顺序调用 collective；
- tensor 的元素数量、dtype 和切分规则满足对应 API 的要求；
- `root`、split size 等参数在各 rank 上相互一致。

违反这些约定时，程序不一定立刻给出明确的错误信息；更常见的现象是某些 rank 永久等待另一些 rank，表现为 **hang**。

## 2. 点对点通信：Send 与 Recv

最基础的通信发生在一对 rank 之间：

```text
R0 -- Send(tensor) --> R1
R1 <-- Recv(tensor) -- R0
```

`Send(src → dst)` 从源 rank 发出一段数据，`Recv(dst ← src)` 在目标 rank 接收与之匹配的数据。它不会自动让其他 rank 得到副本，也不会自动对数据求和。

理想化的单条消息成本可写成：

$$
T_{\text{p2p}}
\approx
\alpha + M\beta
$$

其中：

- $\alpha$ 是启动一次通信的固定延迟；
- $M$ 是消息字节数；
- $\beta=1/B_{\text{eff}}$ 是传输每字节所需时间；
- $B_{\text{eff}}$ 是包含协议与拓扑影响后的有效带宽。

### 2.1 阻塞、非阻塞与“数据真的可用”

很多框架同时提供 `send/recv` 和 `isend/irecv`。非阻塞接口通常会返回一个 handle，允许程序先提交通信、稍后再等待：

```python
send_work = dist.isend(activation, dst=next_rank)

# 这里可以尝试执行不依赖 activation 发送完成的计算
do_independent_compute()

send_work.wait()
```

但“API 已经返回”不等于下面三件事已经自动成立：

1. 数据已经到达对端；
2. 当前计算流可以安全复用发送 buffer；
3. 通信已经与计算产生了有效重叠。

真正的 overlap 还取决于数据依赖、CUDA stream、框架的进展机制，以及通信 kernel 和计算 kernel 是否争抢相同资源。最终应通过 profiler 时间线验证，而不是只看代码中有没有 `async_op=True`。

### 2.2 Pipeline Parallel 为什么使用 P2P？

流水线并行把不同层放在相邻 stage 上。前向时传递边界激活，反向时沿相反方向传递激活梯度：

```text
Forward:
Stage 0 -- activation ------> Stage 1 -- activation ------> Stage 2

Backward:
Stage 0 <-- d(activation) --- Stage 1 <-- d(activation) --- Stage 2
```

每份激活只有下一个 stage 需要，因此用相邻 rank 的 Send/Recv 比让整个组参加 AllGather 更符合数据依赖。

### 2.3 P2P 最常见的坑：双方都在等

如果两个 rank 都先执行可能阻塞的 Send，之后才执行 Recv，就可能形成等待环：

```text
R0: Send to R1 -> Recv from R1
R1: Send to R0 -> Recv from R0
```

常见处理方法包括：

- 一端先 Send、另一端先 Recv；
- 提前提交匹配的 `Irecv` 和 `Isend`，最后统一等待；
- 使用框架提供的 batch P2P 接口；
- 检查 source、destination、tag、shape、dtype 和调用顺序是否匹配。

其中 `tag` 是否可用取决于后端；例如 PyTorch 的 NCCL backend 不支持依赖 `tag` 区分 P2P 消息。

## 3. 围绕 root 的通信：Broadcast、Reduce、Scatter 与 Gather

有些 collective 以一个 `root rank` 为中心。下图中的 root 是组内逻辑参与者，不是 GPU 的物理编号。具体框架 API 可能要求 global rank 或 group-local rank：例如 PyTorch 的 `src`/`dst` 参数使用 global rank，新版 API 另提供 `group_src`/`group_dst` 表示组内 rank；使用 subgroup 时必须看清接口约定。

### 3.1 Broadcast：一份数据复制给所有 rank

假设 root 为 `R0`：

```text
通信前：R0:[A]    R1:[?]    R2:[?]    R3:[?]

Broadcast(root=R0)

通信后：R0:[A]    R1:[A]    R2:[A]    R3:[A]
```

Broadcast 以 root 的 buffer 作为源数据，其他 rank 上对应 buffer 的旧内容会被覆盖。典型用途包括：

- 从一个 rank 向所有工作进程同步初始化参数或随机种子；
- 分发配置、控制信息或 checkpoint 元数据；
- 复制一个只有 root 生成的 tensor。

### 3.2 Reduce：多份数据归约到一个 root

```text
通信前：R0:[A0]   R1:[A1]   R2:[A2]   R3:[A3]

Reduce(SUM, root=R0)

通信后：R0:[A0 + A1 + A2 + A3]
         其他 rank 不获得可依赖的完整结果
```

Reduce 常用于只需在主 rank 上汇总的统计量，例如全局样本数、loss 总和或评估指标。若所有 rank 后续都需要结果，应使用 AllReduce，而不是 Reduce 后再让大家访问 root 的内存。

### 3.3 Scatter：root 把完整数据分发成分片

```text
通信前：R0:[A | B | C | D]

Scatter(root=R0)

通信后：R0:[A]    R1:[B]    R2:[C]    R3:[D]
```

### 3.4 Gather：所有分片集中到 root

```text
通信前：R0:[A]    R1:[B]    R2:[C]    R3:[D]

Gather(root=R0)

通信后：R0:[A | B | C | D]
```

Scatter 与 Gather 在输入分发、推理结果回收和 checkpoint 处理中很直观，但 root 会成为容量或带宽集中点。大规模 GPU 训练的核心数据路径更常使用没有单一 root 的 AllGather、ReduceScatter 和 AllReduce。

## 4. AllGather：从每人一片到每人一份完整数据

AllGather 的语义是：**每个 rank 提供一个分片，所有 rank 按 rank 顺序得到完整拼接结果。**

```text
通信前：
R0:[A]    R1:[B]    R2:[C]    R3:[D]

AllGather

通信后：
R0:[A | B | C | D]
R1:[A | B | C | D]
R2:[A | B | C | D]
R3:[A | B | C | D]
```

AllGather **只拼接，不做求和**。如果每个分片大小为 $m$ bytes，通信组大小为 $p$，那么每个 rank 的最终输出大小是：

$$
M = p m
$$

它的典型用途包括：

- FSDP/ZeRO-3 在计算前把参数分片临时还原成完整参数；
- Tensor/Sequence Parallel 在某个算子需要完整输入时恢复激活；
- 汇总每个 rank 生成的固定大小结果。

AllGather 不只消耗链路带宽，还会产生完整输出的**瞬时显存占用**。这正是 FSDP 需要按 layer/block 划分通信单元，而不是一次 AllGather 整个模型的重要原因。

### 4.1 AllGather 与 Gather 的区别

```text
Gather:    只有 root 得到 [A | B | C | D]
AllGather: 每个 rank 都得到 [A | B | C | D]
```

多出来的 `All` 不是修饰语，而是明确说明“所有参与者都有结果”。

## 5. ReduceScatter：一边归约，一边保留分片

ReduceScatter 的输入不是“每个 rank 一小片”，而通常是**每个 rank 都有一份完整逻辑长度的输入**。它先按位置归约，再把归约结果分给不同 rank。

4 个 rank 的输入如下：

```text
R0: [A0 | B0 | C0 | D0]
R1: [A1 | B1 | C1 | D1]
R2: [A2 | B2 | C2 | D2]
R3: [A3 | B3 | C3 | D3]
```

执行求和 ReduceScatter 后：

```text
R0: [A0 + A1 + A2 + A3]
R1: [B0 + B1 + B2 + B3]
R2: [C0 + C1 + C2 + C3]
R3: [D0 + D1 + D2 + D3]
```

所以 ReduceScatter 同时完成两件事：

1. 对所有 rank 的对应位置做 Reduce；
2. 让第 $r$ 个 rank 只保留归约结果中的第 $r$ 个 shard。

“先 Reduce 到 root，再由 root Scatter”可以帮助理解结果，但高效实现会把归约和分发融合、流水化，并不需要在某个 root 上物化完整结果。

ReduceScatter 特别适合“每份局部结果必须求和，但下一步每个 rank 只负责其中一片”的场景：

- FSDP/ZeRO 把数据并行梯度聚合后留在参数 owner 上；
- Distributed Optimizer 只让每个 rank 更新自己负责的参数分片；
- Sequence Parallel 将原本复制的输出改为沿序列维保留分片。

### 5.1 ReduceScatter 不是 AllGather 的数学逆运算

两者的数据布局恰好互补：

```text
AllGather:      分片  -> 每人完整
ReduceScatter: 每人完整 -> 归约后的分片
```

但 ReduceScatter 做了归约，多个输入的信息已经合并，因此它在一般意义上不可逆。准确的说法是：**两者在通信结构上互补，并可组合成 AllReduce。**

## 6. AllReduce：归约后让每个 rank 都得到结果

AllReduce 是数据并行训练中最常见的 collective。每个 rank 输入形状相同的 tensor，所有输入逐元素归约，最终每个 rank 都得到相同结果：

```text
通信前：R0:[A0]   R1:[A1]   R2:[A2]   R3:[A3]

AllReduce(SUM)

通信后：
R0:[A0 + A1 + A2 + A3]
R1:[A0 + A1 + A2 + A3]
R2:[A0 + A1 + A2 + A3]
R3:[A0 + A1 + A2 + A3]
```

### 6.1 AllReduce 不等于“自动求平均”

AllReduce 接受一个归约运算，例如 `SUM`、`MAX` 或 `MIN`。分布式训练中常见的是求和：

$$
g_{\text{sum}} = \sum_{r=0}^{p-1} g_r
$$

全局平均梯度还需要：

$$
g_{\text{mean}}
=
\frac{1}{p}\sum_{r=0}^{p-1}g_r
$$

这个公式假设各 rank 的有效样本数（或有效 token 数）相同，并且每个 $g_r$ 都是同口径的局部均值。若第 $r$ 个 rank 的有效样本数为 $n_r$，不等长 batch 的全局样本平均应按样本数加权：

$$
g_{\text{mean}}
=
\frac{\sum_r n_r g_r}{\sum_r n_r}
$$

这个除法可能由框架在 collective 之前或之后完成，也可能通过 loss 的定义间接体现。看到底层调用 `SUM`，不能立刻断言梯度被放大了 $p$ 倍；必须结合框架的完整缩放语义判断。

### 6.2 AllReduce = ReduceScatter + AllGather

把每个 rank 的输入切成 $p$ 片：

```text
第一阶段 ReduceScatter：
每个 rank 得到归约结果的一片

R0:[ΣA]    R1:[ΣB]    R2:[ΣC]    R3:[ΣD]

第二阶段 AllGather：
交换这 4 个归约分片

R0:[ΣA | ΣB | ΣC | ΣD]
R1:[ΣA | ΣB | ΣC | ΣD]
R2:[ΣA | ΣB | ΣC | ΣD]
R3:[ΣA | ΣB | ΣC | ΣD]
```

因此：

$$
\text{AllReduce}
\equiv
\text{ReduceScatter}
+
\text{AllGather}
$$

这条关系有两个价值：

1. 它解释了 Ring AllReduce 为什么自然分成两个阶段；
2. 它解释了为什么 sharded training 可以在 ReduceScatter 后停下来，只保存分片，把 AllGather 延迟到真正需要完整参数时再做。

### 6.3 DDP 为什么需要 AllReduce？

数据并行的每个 rank 拥有相同参数，但处理不同 mini-batch：

```text
R0: model W + batch 0 -> local gradient g0
R1: model W + batch 1 -> local gradient g1
R2: model W + batch 2 -> local gradient g2
R3: model W + batch 3 -> local gradient g3
```

如果各 rank 直接用不同的 $g_r$ 更新，模型副本会在一步之后分叉。假设 4 个 local batch 的有效样本数相同，且各 $g_r$ 是 local mean，AllReduce 让它们得到相同的全局平均梯度，再执行相同更新：

```text
g = AllReduce(g0, g1, g2, g3) / 4

R0: W <- update(W, g)
R1: W <- update(W, g)
R2: W <- update(W, g)
R3: W <- update(W, g)
```

实际 DDP 通常把许多参数的梯度装入 bucket。某个 bucket 在 backward 中就绪后立刻发起 AllReduce，从而尝试把梯度通信隐藏在剩余反向计算之后。

## 7. AllToAll：把数据按目的地重新路由

AllToAll 不是“所有 rank 都收集所有数据”。它的语义更像一次**分布式转置**：每个 rank 把输入切成 $p$ 份，其中第 $j$ 份发给 rank $j$。

令 $X_{ij}$ 表示“源 rank $i$ 要发给目标 rank $j$ 的数据”：

```text
通信前：
R0: [X00 | X01 | X02 | X03]
R1: [X10 | X11 | X12 | X13]
R2: [X20 | X21 | X22 | X23]
R3: [X30 | X31 | X32 | X33]

AllToAll

通信后：
R0: [X00 | X10 | X20 | X30]
R1: [X01 | X11 | X21 | X31]
R2: [X02 | X12 | X22 | X32]
R3: [X03 | X13 | X23 | X33]
```

它不做求和，也不会让每个 rank 拥有所有 $X_{ij}$；它只是根据目的 rank 重排所有分片。

### 7.1 MoE 为什么需要 AllToAll？

在 Expert Parallel 中，不同专家被放在不同 rank。router 为 token 选择专家后，需要把 token 发到对应专家所在设备：

```text
原始 token
   │
   ├─ pack by destination expert
   ▼
AllToAll / AllToAllv       # dispatch
   │
   ▼
local expert compute
   │
   ▼
AllToAll / AllToAllv       # combine / return
   │
   ▼
恢复原 token 顺序
```

真实路由通常不均匀：一个 rank 可能给不同目标发送不同数量的 token，因此实现常需要可变 split size 的 AllToAllv 或等价接口。性能不仅取决于总字节数，还取决于：

- 最热门专家所在 rank 的负载；
- Top-$k$ 路由带来的 token 复制；
- capacity padding 与丢弃策略；
- pack/unpack kernel；
- 跨节点网络的双截带宽和拥塞。

Collective 的完成时间常由最慢的 rank 决定，因此平均 token 数看起来均衡，并不代表尾部延迟没有问题。

## 8. Barrier：同步控制流，不搬运模型数据

Barrier 没有需要交换的业务 tensor。它表达的是：**当前 process group 中的所有 rank 都到达这个同步点后，大家才能继续。**

```text
到达顺序：R1 -> R3 -> R0 -> R2

R1、R3、R0：到达后等待
R2：最后到达 -> group 被统一放行 -> 所有 rank 继续
```

Barrier 适合：

- 确保初始化阶段全部完成后再训练；
- 协调由某个 rank 创建、其他 rank 随后读取的外部资源；
- 在设计正确的 benchmark 中建立统一测量边界。

Barrier 不适合被当成“哪里不同步就加哪里”的万能修复。它不能替代：

- 正确匹配的 Send/Recv；
- 一致的 collective 调用顺序；
- 对异步 work handle 的正确等待；
- 正确的 CUDA stream/event 依赖。

而且 Barrier 自身也是同步点；放在训练热路径中会让较快 rank 等待最慢 rank，可能掩盖真正的负载不均。

## 9. 一张表看懂常见通信原语

下面统一令 $p$ 为通信组大小，$M$ 为一个**完整逻辑 tensor** 的字节数。表格描述的是语义，不指定 Ring 或 Tree 等实现算法。

| 原语            | 通信前                        | 通信后                         | 是否归约 | 分布式训练中的典型用途            |
| ------------- | -------------------------- | --------------------------- | ---: | ---------------------- |
| Send/Recv     | source 有 $M$               | destination 得到 $M$          |    否 | PP 传递激活与激活梯度           |
| Broadcast     | root 有 $M$                 | 每个 rank 有相同的 $M$            |    否 | 参数初始化、控制信息             |
| Reduce        | 每个 rank 有 $M$              | 只有 root 有归约后的 $M$           |    是 | 汇总指标到主 rank            |
| Scatter       | root 有 $M$                 | 每个 rank 有 $M/p$             |    否 | 从中心分发分片                |
| Gather        | 每个 rank 有 $M/p$            | 只有 root 有拼接后的 $M$           |    否 | 向中心收集分片                |
| AllGather     | 每个 rank 有 $M/p$            | 每个 rank 有拼接后的 $M$           |    否 | 恢复完整参数或激活              |
| ReduceScatter | 每个 rank 有 $M$              | 每个 rank 有归约后的 $M/p$         |    是 | 分片梯度、Sequence Parallel |
| AllReduce     | 每个 rank 有 $M$              | 每个 rank 有归约后的 $M$           |    是 | DDP 梯度、TP 局部和          |
| AllToAll      | 每个 rank 有 $p$ 个目标分片，总计 $M$ | 每个 rank 收到所有 source 发给自己的分片 |    否 | MoE token 路由、布局转置      |
| Barrier       | 无业务 payload                | 所有 rank 在同一控制点后继续           |    否 | 阶段同步、调试与测量             |

这里有三组最容易混淆的对照：

```text
Gather         只有 root 得到完整拼接结果
AllGather      所有 rank 都得到完整拼接结果

Reduce         只有 root 得到归约结果
AllReduce      所有 rank 都得到归约结果

AllGather      拼接分片，不归约
AllToAll       按目标重新路由，不让每人持有全集
```

## 10. 通信原语在反向传播中的对应关系（进阶）

通信不仅出现在 forward 中。若一个可微 tensor 穿过 collective，backward 必须按照该通信算子的伴随变换，把各 rank 上的梯度贡献传播到对应输入。直观上，forward 若复制了一份数据，backward 就要把多份梯度相加；forward 若拆分了数据，backward 往往要把梯度重新拼接。

以求和归约为例，下表给出常见的线性伴随关系：

| Forward 中的数据变换 | Backward 中对应的数据变换 | 直觉 |
|---|---|---|
| Broadcast | Reduce 到 root | root 的同一份输入影响了所有 rank，梯度要加回 root |
| Reduce 到 root | Broadcast | 每个输入都影响 root 的归约结果，root 梯度要发回所有输入方 |
| AllGather | ReduceScatter | 每个分片被所有 rank 使用，对该分片的梯度要跨 rank 求和后回到 owner |
| ReduceScatter | AllGather | 各输出分片的梯度需要拼成每个完整输入的梯度 |
| AllReduce(SUM) | AllReduce(SUM) | 每个输入影响每个 rank 上的同一归约结果 |
| AllToAll | 反向 split 的 AllToAll | 把梯度按原路由关系送回 source |
| Send | 反方向的 Recv/Send | 梯度沿计算图反向返回 |

例如，AllGather 的 forward 是：

```text
R0:[A]  R1:[B]  ->  两边都得到 [A | B]
```

若两边都基于完整结果计算本地 loss，那么属于 `A` 的梯度会在 R0 和 R1 上各产生一份。Backward 需要把这两份梯度求和，并只把 `A` 对应的结果留给 R0；这恰好是 ReduceScatter 的语义。

这个视角能解释许多张量并行代码中看似“成对出现”的 collective。需要注意：上表描述数学关系；某个框架的具体 API 是否原生支持 autograd、如何处理异步执行和 uneven split，仍要查看其实现。

## 11. 通信到底有多贵？延迟、带宽与归约成本

只写“大约传了 $M$ bytes”不足以预测耗时。一个更有用的理想化模型是：

$$
T_{\text{comm}}
\approx
s\alpha
+
V\beta
+
R\gamma
$$

其中：

- $s$：关键路径上的通信轮数；
- $\alpha$：每轮的启动延迟；
- $V$：对称算法中每个 rank 发出的 payload；非对称算法中应关注瓶颈 rank 或瓶颈链路的有效 payload；
- $\beta$：每字节的传输成本；
- $R$：需要在本地执行归约的数据量；
- $\gamma$：每字节归约计算的成本。

后续公式均假设分片均匀、调度固定，并忽略 padding、协议头、拓扑争用和慢 rank；它们用于比较量级，不是任意后端上的实测时间预测式。

为了避免“差一倍”的争论，后文采用统一口径：

> **通信量指每个 rank 累计发出的 payload；在对称 Ring 中，每个 rank 的累计接收量通常与发送量相同。若把发送和接收相加，需要再乘 2；物理链路的逐跳流量又是另一种口径。**

### 11.1 Ring AllGather 与 Ring ReduceScatter

设 $M$ 为最终完整逻辑 tensor 的大小。Ring 把它切成 $p$ 片，每片 $M/p$ bytes。

AllGather 经过 $p-1$ 轮，每轮每个 rank 发送一个分片：

$$
T_{\text{ring-AG}}
\approx
(p-1)\alpha
+
\frac{p-1}{p}M\beta
$$

每个 rank 累计发送：

$$
V_{\text{ring-AG}}
=
\frac{p-1}{p}M
$$

ReduceScatter 也经过 $p-1$ 轮，但收到分片后还要执行归约：

$$
T_{\text{ring-RS}}
\approx
(p-1)\alpha
+
\frac{p-1}{p}M\beta
+
\frac{p-1}{p}M\gamma
$$

### 11.2 Ring AllReduce

Ring AllReduce 由 $p-1$ 轮 ReduceScatter 和 $p-1$ 轮 AllGather 组成：

$$
T_{\text{ring-AR}}
\approx
2(p-1)\alpha
+
2\frac{p-1}{p}M\beta
+
\frac{p-1}{p}M\gamma
$$

每个 rank 累计发送量为：

$$
V_{\text{ring-AR}}
=
2\frac{p-1}{p}M
$$

例如，8 个 rank 对 1 GiB 梯度执行 Ring AllReduce，每个 rank 的理想累计发送量是：

$$
2\times\frac{7}{8}\times1\ \text{GiB}
=
1.75\ \text{GiB}
$$

接收量也约为 1.75 GiB。这个数字不能直接除以网卡标称带宽来断言训练耗时，因为实际还包含协议效率、拓扑、链路争用、归约 kernel、同步等待，并且一部分通信可能被计算隐藏。

### 11.3 Pairwise AllToAll

若每个 rank 的输入总计为 $M$，并均匀切给 $p$ 个目标，其中 $M/p$ 留在本地，那么 pairwise exchange 的理想发送量为：

$$
V_{\text{A2A}}
=
\frac{p-1}{p}M
$$

理想化时间可写成：

$$
T_{\text{A2A}}
\approx
(p-1)\alpha
+
\frac{p-1}{p}M\beta
$$

但 AllToAll 会同时形成许多 source-destination 流，真实表现对网络双截带宽、rank 映射、消息碎片和不均匀 split 极其敏感。上式只是均匀切分、近似单端口的 pairwise-exchange 调度下的粗略模型；其他实现可以采用不同并发与轮次。

### 11.4 Ring、Tree 与分层算法怎么选？

大致可以这样理解：

| 算法思路 | 优势 | 代价 | 常见适用区间 |
|---|---|---|---|
| Ring | 链路负载均匀，大消息容易逼近带宽上限 | 轮数随 $p$ 线性增长 | 大 tensor、带宽主导 |
| Tree | 关键路径轮数可为 $O(\log p)$ | 具体带宽项取决于是否分块及树结构 | 小 tensor、延迟主导 |
| Recursive Halving/Doubling | 对数轮数，同时可保持较好的带宽项 | 常要求规则切分，调度更复杂 | 中小消息或特定规模 |
| Hierarchical | 先用高速节点内链路，再跨节点，再节点内分发 | 需要感知拓扑与层级 | 多机多卡 |

不要把“Tree”简单等同于固定的 $M\log p$ 带宽开销：分块树和递归折半/倍增算法可以有不同的数据量。实际 NCCL、MPI 等通信库会综合消息大小、rank 数、链路和协议选择算法。

### 11.5 三个性能区间

通信瓶颈通常落在三个区间：

1. **小消息，延迟主导**：$s\alpha$ 最大。重点是融合小 tensor、减少 collective 次数；
2. **大消息，带宽主导**：$V\beta$ 最大。重点是拓扑、链路利用率、dtype 与分层算法；
3. **中等消息，调度主导**：分块大小、kernel 排队、计算重叠和资源竞争共同决定结果。

因此，1000 次 1 KiB collective 通常不能用“一共只有 1 MiB”来解释；每次启动延迟可能才是主要成本。

### 11.6 真正影响步时的是 exposed communication

训练一步可以粗略拆成：

$$
T_{\text{step}}
\approx
T_{\text{compute}}
+
T_{\text{exposed-comm}}
+
T_{\text{bubble}}
+
T_{\text{other}}
$$

如果一段通信与独立计算完全重叠，它仍占用链路和 GPU 资源，却未必等量增加 wall-clock step time。优化时应关注没有被隐藏的 `exposed communication`，同时确认所谓 overlap 没有让计算 kernel 明显变慢。

## 12. 这些原语如何组成分布式训练策略？

先看总览：

| 并行策略 | 主要被切分的数据 | 核心通信原语 | 通信通常发生在哪里 |
|---|---|---|---|
| Data Parallel / DDP | batch | 梯度 AllReduce | 每次 backward，按 bucket |
| Distributed Optimizer / ZeRO-1/2 | 优化器状态、梯度 | ReduceScatter + AllGather 或等价同步 | optimizer step 前后 |
| FSDP / ZeRO-3 | 参数、梯度、优化器状态 | 参数 AllGather + 梯度 ReduceScatter | 按 layer/block 的前反向 |
| Tensor Parallel | 权重与激活维度 | AllReduce、AllGather、ReduceScatter | 几乎每个 Transformer block |
| Sequence Parallel | sequence 维激活 | AllGather、ReduceScatter | 需要改变激活布局的边界 |
| Pipeline Parallel | layers/stages | Send/Recv | 相邻 stage，每个 micro-batch |
| Expert Parallel / MoE | experts 与 routed tokens | AllToAll / AllToAllv | 每个 MoE layer 的 dispatch/combine |
| Context Parallel | 长序列上下文 | P2P Ring、AllGather 或 AllToAll | attention 内部，依实现而定 |

### 12.1 DDP：对梯度执行 AllReduce

DDP 的每个 DP rank 持有完整参数和优化器状态，并在反向过程中产生完整的局部梯度。各 rank 处理不同数据，再把局部梯度 AllReduce 成相同结果。

高效 DDP 通常采用：

- **gradient bucketing**：把许多小梯度拼成更大的 collective；
- **overlap**：某个 bucket 的梯度就绪后，立即与剩余 backward 重叠；
- **gradient accumulation**：累积若干 micro-batch 后再同步一次；
- **固定 bucket 顺序**：让所有 rank 以相同顺序进入 collective。

DDP 的目的不仅是“把梯度加起来”，还必须保证每个副本随后用完全一致的同步梯度更新。

### 12.2 FSDP / ZeRO-3：参数 AllGather，梯度 ReduceScatter

完全分片数据并行让每个 rank 平时只保存模型状态的一片。计算当前单元前临时恢复完整参数，反向完成后只留下聚合梯度的一片：

```text
稳定状态：
R0:[W0]    R1:[W1]    R2:[W2]    R3:[W3]

进入某个 FSDP 单元：
AllGather(W shards)
    -> 每个 rank 临时得到完整 W
    -> 各自处理不同 batch 的 forward/backward

离开该单元：
ReduceScatter(local dW)
    -> Rr 只保留全局 dWr
    -> 本地 optimizer 更新 Wr
```

若 forward 后立刻 reshard 参数，backward 计算该单元前通常还需要再次 AllGather；若保留完整参数到 backward，则节省一次通信但提高峰值显存。更多细节可继续阅读 [[FSDP|《FSDP：把模型状态拆散到多张 GPU 上》]]。

一个容易误解的结论是：**FSDP/ZeRO 首要收益是分片显存，而不是让通信凭空消失。** ReduceScatter + AllGather 的字节量可以与一次 Ring AllReduce 同量级；完全分片还可能因为参数在 forward/backward 的按需重建增加通信。性能取决于通信粒度、预取、reshard 策略与 overlap。

### 12.3 ZeRO-1/2：把归约结果直接交给 owner

ZeRO 的各阶段逐步分片优化器状态、梯度和参数。对 ZeRO-1/2，高效实现可以：

1. 用 ReduceScatter 把归约后的梯度分片交给负责它的 rank；
2. 每个 rank 只更新自己负责的参数分片；
3. 再用 AllGather 或等价机制同步更新后的参数。

不同框架会对参数驻留、梯度 buffer 和同步时机做不同调度，不应把某个具体调用序列写成所有 ZeRO 实现的唯一规范。稳定的心智模型是：**谁负责更新某个参数，谁就只需要最终归约后属于那一片的梯度。**

### 12.4 Tensor Parallel：通信嵌入每一层

以线性层 $Y=XW$ 为例。

按输出维切分权重（Column Parallel）：

```text
W = [W0 | W1 | W2 | W3]
Yr = XWr
```

每个 rank 的前向输出天然是一个分片；若下一层接受这种布局，可以暂时不通信。若下一步需要完整 $Y$，再做 AllGather。反向时，每个 shard 对输入梯度产生局部贡献，通常需要 AllReduce 或等价的 ReduceScatter 来合并。

按输入维切分权重（Row Parallel）：

```text
X = [X0 | X1 | X2 | X3]
W 按对应行切分为 W0...W3
local Yr = XrWr
Y = Σ local Yr
```

各 rank 得到的是输出的部分和，前向通常需要 AllReduce；若希望输出继续保持 sequence shard，也可以使用 ReduceScatter 改变布局。

TP 的 collective 往往每层发生，频率远高于每步一次的粗粒度同步，对延迟非常敏感。因此 TP group 通常尽量放在 NVLink/NVSwitch 等节点内高速互联域。

### 12.5 Sequence Parallel：在完整与分片激活之间切换

Sequence Parallel 常把沿序列维复制的激活改成分片状态：

```text
需要完整输入：AllGather(sequence shards)
计算后继续分片：ReduceScatter(output contributions)
```

它不仅影响通信，也改变激活的常驻显存。把 AllReduce 拆成 ReduceScatter + 延迟执行的 AllGather，正是“相同的归约语义，不同的中间数据布局与显存生命周期”的典型例子。

### 12.6 Pipeline Parallel：相邻 stage 的 Send/Recv

PP 不需要让所有 stage 都看到同一份边界激活，因此核心原语是邻接 P2P。micro-batch 调度决定通信频率与流水线气泡：

```text
micro-batch 0: S0[F] -> S1[F] -> S2[F]
micro-batch 1:     S0[F] -> S1[F] -> S2[F]
backward:                    S2[B] -> S1[B] -> S0[B]
```

增加 micro-batch 数通常可以减小 bubble，却会增加消息次数和调度复杂度。混合并行时，每个 pipeline stage 内的 DP 副本还会另外执行梯度 AllReduce/ReduceScatter。

### 12.7 Expert Parallel：forward 通常需要两次 AllToAll

MoE layer 一般需要：

1. dispatch：根据 router 结果把 token 发到专家所在 rank；
2. local expert compute；
3. combine：把专家输出发回 token 原来的计算布局。

因此一次 forward 中常看到成对的 AllToAll；训练时 backward 通常还会执行两次对应的反向 AllToAll。若路由极不均衡，最快 rank 也必须等待最忙的专家 rank；这既是计算负载问题，也是通信尾延迟问题。

### 12.8 混合并行：同一个 rank 属于多个 group

仅考虑正交的 DP × TP × PP 三维并行，且暂不把 EP/CP 视为额外独立维度时，假设总 GPU 数满足：

$$
N_{\text{GPU}}
=
N_{\text{DP}}
\times
N_{\text{TP}}
\times
N_{\text{PP}}
$$

可以把每个 rank 想成一个坐标 $(d,t,s)$，其中 $s$ 表示 pipeline stage，避免与前文的通信组大小 $p$ 混淆：

- DP collective：固定 $(t,s)$，只改变 $d$；
- TP collective：固定 $(d,s)$，只改变 $t$；
- PP P2P：固定 $(d,t)$，在相邻 $s$ 之间通信。

如果误用全局 WORLD group，不仅会多传数据，还可能让语义完全错误。**先确认 group，再分析 collective。**

## 13. 一个可运行的 PyTorch 小实验

下面的程序在 4 张 CUDA GPU 上演示 Broadcast、AllReduce、AllGather、ReduceScatter 和 AllToAll。它使用 NCCL，因此每个进程必须先绑定自己的 GPU。

```python
import os

import torch
import torch.distributed as dist


def main():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    device = torch.device("cuda", local_rank)

    dist.init_process_group(backend="nccl")
    rank = dist.get_rank()
    world_size = dist.get_world_size()
    if world_size != 4:
        raise RuntimeError("This demo expects exactly 4 ranks")

    # 1) Broadcast: 只有 R0 的值会成为结果
    broadcast_value = torch.tensor(
        [100.0 if rank == 0 else -1.0], device=device
    )
    dist.broadcast(broadcast_value, src=0)

    # 2) AllReduce: 0 + 1 + 2 + 3 = 6
    local_value = torch.tensor([float(rank)], device=device)
    reduced = local_value.clone()
    dist.all_reduce(reduced, op=dist.ReduceOp.SUM)

    # 3) AllGather: 每个 rank 都得到 [0, 1, 2, 3]
    gathered = torch.empty(world_size, device=device)
    dist.all_gather_into_tensor(gathered, local_value)

    # 4) ReduceScatter:
    # Rr 的输入为 [10r, 10r+1, 10r+2, 10r+3]
    # 第 j 个位置跨 rank 求和为 60 + 4j，结果第 j 片留给 Rj
    rs_input = rank * 10 + torch.arange(
        world_size, dtype=torch.float32, device=device
    )
    rs_output = torch.empty(1, device=device)
    dist.reduce_scatter_tensor(
        rs_output, rs_input, op=dist.ReduceOp.SUM
    )

    # 5) AllToAll:
    # Rr 输入的第 j 个数发给 Rj
    # 因此 Rj 收到 [j, 10+j, 20+j, 30+j]
    a2a_input = rank * 10 + torch.arange(
        world_size, dtype=torch.float32, device=device
    )
    a2a_output = torch.empty_like(a2a_input)
    dist.all_to_all_single(a2a_output, a2a_input)

    # 尽量按 rank 顺序打印，flush 减少多进程 stdout 缓冲造成的乱序。
    for print_rank in range(world_size):
        dist.barrier()
        if rank == print_rank:
            print(
                f"R{rank}: "
                f"broadcast={broadcast_value.tolist()}, "
                f"all_reduce={reduced.tolist()}, "
                f"all_gather={gathered.tolist()}, "
                f"reduce_scatter={rs_output.tolist()}, "
                f"all_to_all={a2a_output.tolist()}",
                flush=True,
            )

    dist.destroy_process_group()


if __name__ == "__main__":
    main()
```

保存为 `primitives_demo.py` 后运行：

```bash
torchrun --standalone --nproc-per-node=4 primitives_demo.py
```

预期核心结果为：

```text
R0: broadcast=[100.0], all_reduce=[6.0], all_gather=[0.0, 1.0, 2.0, 3.0], reduce_scatter=[60.0], all_to_all=[0.0, 10.0, 20.0, 30.0]
R1: broadcast=[100.0], all_reduce=[6.0], all_gather=[0.0, 1.0, 2.0, 3.0], reduce_scatter=[64.0], all_to_all=[1.0, 11.0, 21.0, 31.0]
R2: broadcast=[100.0], all_reduce=[6.0], all_gather=[0.0, 1.0, 2.0, 3.0], reduce_scatter=[68.0], all_to_all=[2.0, 12.0, 22.0, 32.0]
R3: broadcast=[100.0], all_reduce=[6.0], all_gather=[0.0, 1.0, 2.0, 3.0], reduce_scatter=[72.0], all_to_all=[3.0, 13.0, 23.0, 33.0]
```

多进程日志仍可能受启动器的 stdout 汇集方式影响而轻微乱序。这个例子故意让 tensor 很小，只用于验证**语义**，不能用于衡量 NCCL 性能。

## 14. 如何选择正确的原语？

选择原语时，不要先问“哪个 API 最常用”，而要依次问：

1. 通信前，完整数据或各分片位于哪些 rank？
2. 通信后，哪些 rank 需要完整结果，哪些只需要一片？
3. 是否需要对多个输入执行 SUM/MAX 等归约？
4. 数据是复制给所有人，还是每个目的地收到不同内容？
5. 该通信位于关键路径吗？更应该优化延迟、带宽、显存还是 overlap？

可以压缩成下面这棵决策树：

```text
只需要控制流会合，不搬运业务数据？
├─ 是：Barrier
└─ 否：需要搬运数据
   ├─ 只在一对 rank 之间传输：Send/Recv
   └─ 多个 rank 参与
      ├─ 是否需要归约？
      │  ├─ 是
      │  │  ├─ 只有 root 要结果：Reduce
      │  │  ├─ 每个 rank 都要完整结果：AllReduce
      │  │  └─ 每个 rank 只要归约结果的一片：ReduceScatter
      │  └─ 否
      │     ├─ root 的同一份数据给所有人：Broadcast
      │     ├─ 分片拼接后只有 root 要：Gather
      │     ├─ 分片拼接后每个人都要：AllGather
      │     ├─ root 把完整数据切给大家：Scatter
      │     └─ 每个目标收到不同内容：AllToAll
```

一个非常实用的优化原则是：

> **若下一步只需要归约结果的一片，就直接用 ReduceScatter，不要 AllReduce 完再切掉其余 $p-1$ 片；若只有 root 需要结果，就不要让 AllReduce 把结果复制给所有人。**

## 15. 优化通信的八个抓手

### 15.1 减少小消息：融合与 bucketing

当 $\alpha$ 主导时，合并 100 个小 collective 通常比微调单次 payload 更有效。DDP gradient bucket、参数 flatten、MoE token packing 都在做类似的事。

bucket 也不能无限大：太大的 bucket 会等到更多梯度就绪后才启动，损失 overlap 机会，并提高临时 buffer 显存。合适大小应通过 profiler 调整。

### 15.2 选择符合最终布局的原语

- 需要归约，且每个 rank 最终只保留一个 shard：ReduceScatter；
- 需要归约，且所有 rank 最终都要完整结果：AllReduce；
- 不需要归约，只需把分片拼成完整值：AllGather；
- 每个目的地的数据不同：AllToAll，而不是多次 Broadcast；
- 只有相邻 stage 需要数据：P2P，而不是全组 collective。

少搬不需要的数据，通常比事后压榨几个百分点带宽更有价值。

### 15.3 把通信与独立计算重叠

有效 overlap 必须同时满足：

- 通信足够早发起；
- 后续有一段不依赖其结果的计算；
- buffer 生命周期与 stream/event 依赖正确；
- 通信和计算并发后没有严重资源争抢；
- 最终在真正使用结果之前等待完成。

典型例子是 DDP backward bucket overlap，以及 FSDP 预取下一单元参数的 AllGather。

### 15.4 使用合适的通信 dtype

把 FP32 payload 改为 BF16/FP16 可以减少字节数，但这会改变数值行为。需要区分：

- 线上传输 dtype；
- 本地归约累加精度；
- optimizer 保留的梯度/状态精度；
- 是否使用压缩、量化与 error feedback。

“通信减半”不自动等于“step time 减半”，更不自动保证收敛完全一致。

### 15.5 让 process group 顺应物理拓扑

典型多机系统有明显层级：

```text
同一 GPU 内存
   ↕
节点内 GPU：NVLink / NVSwitch / PCIe
   ↕
节点间 NIC：InfiniBand / RoCE / Ethernet
```

高频、细粒度 TP 通信通常放在节点内高速域；DP 可以跨节点；分层 collective 先在节点内归约，再减少跨节点流量。rank 到 GPU、NUMA 和 NIC 的映射会直接影响性能。

### 15.6 处理不均匀与 padding

很多高效 collective 对等长、连续、对齐的 tensor 最友好。真实 workload 却可能出现：

- 参数量不能被 group size 整除；
- variable-length sequence；
- MoE 每个目标的 token 数不同；
- 最后一个 data batch 较小。

需要明确 split size、padding 与有效长度，不能让不同 rank 对 count 的理解不一致。MoE 还要同时观察 token 均衡和 expert 计算均衡。

### 15.7 避免无意义的全局同步

一次不必要的 Barrier 会把局部抖动传播成全局等待；一次误用 WORLD group 的 AllReduce 会让本应在 8 卡内完成的 TP 通信跨越整个集群。缩小同步范围，与减少字节数同样重要。

### 15.8 用时间线和基准说话

建议同时观察：

- 各 collective 的 GPU 起止时间与调用次数；
- tensor size、dtype、process group 和算法；
- 与 compute kernel 的重叠比例；
- 各 rank 的最慢完成时间，而不只是平均值；
- 链路利用率、算法带宽与 bus bandwidth 的统计口径；
- 单独通信 microbenchmark 与完整训练 step 的差异。

benchmark 应先预热，在正确的 host/device 同步边界测量，并报告中位数与尾延迟。只用 Python 墙钟包住一个异步 CUDA 调用，通常测不到真实完成时间。

## 16. Collective 卡住、结果不对或特别慢时怎么查？

### 16.1 卡住：先检查调用图是否一致

按优先级检查：

1. 是否有 rank 根本没有进入该 collective？
2. 所有 rank 使用的 process group 是否相同？
3. collective 的调用顺序是否相同？
4. tensor 的 count、shape、dtype 和 device 是否兼容？
5. root、source/destination、tag 和 split size 是否一致？
6. 某个 rank 是否早已 OOM、异常退出或阻塞在 dataloader？

例如下面的条件分支会挂住：

```python
if rank == 0:
    dist.all_reduce(x)  # 其他 rank 没有参与
```

正确思路通常是让所有 group 成员调用 collective，只把结果处理放进 rank 条件：

```python
dist.all_reduce(x)
if rank == 0:
    consume(x)
```

### 16.2 不挂但结果不对：检查布局与缩放

重点检查：

- 把 AllGather 误当成求和；
- 把 AllToAll 的接收顺序误当成原顺序；
- ReduceScatter 的 shard index 与参数 owner 不一致；
- SUM 后漏除或重复除以 DP size；
- 不同 group 的 rank 顺序导致拼接顺序变化；
- 异步操作完成前复用了 buffer；
- padding 区域没有在后续计算中 mask。

浮点归约还可能因为 Ring 与 Tree 的加法顺序不同而产生微小数值差异。浮点加法不满足严格结合律，这不一定代表通信出错。

### 16.3 正确但很慢：判断是哪一类瓶颈

| 现象 | 更可能的原因 | 优先动作 |
|---|---|---|
| 大量几 KiB collective | 启动延迟 | 融合 tensor、调整 bucket |
| 大 tensor 带宽远低于预期 | 拓扑、算法、NIC/NUMA、链路争用 | 检查 rank 映射与通信基准 |
| 通信时间线与计算完全串行 | 依赖过早、异步调度无效 | 调整预取/bucket，检查 stream |
| 只有个别 rank 晚很多 | 数据或 expert 负载不均 | 看逐 rank 时间与 token/batch 分布 |
| 跨节点后断崖式下降 | 节点间链路成为瓶颈 | 分层通信、调整并行维度布局 |
| AllGather 后 OOM | 完整 tensor 与临时 buffer 峰值 | 缩小通信单元、延迟 materialize |

## 17. 十个常见误解

### 误解一：AllReduce 就是 Ring

AllReduce 是结果语义；Ring 是实现算法之一。通信库也可能选择 Tree、递归算法或分层方案。

### 误解二：AllReduce 天然返回平均值

它执行指定的归约。训练框架可能在其他位置除以 data-parallel size。

### 误解三：AllGather 会把各 rank 的 tensor 相加

不会。AllGather 按 rank 顺序拼接分片；做加法的是 Reduce 系列原语。

### 误解四：AllToAll 之后每个 rank 拿到全集

不会。每个 rank 只收到所有 source 专门发给它的那一片。

### 误解五：ReduceScatter 是 AllGather 的数学逆操作

数据布局互补，但归约会合并信息，因此一般不可逆。

### 误解六：异步 API 返回就说明通信完成了

返回通常只表示工作已提交。何时能访问或复用 buffer，要看 work handle 和执行流同步语义。

### 误解七：通信量相同，耗时就相同

轮数、消息粒度、拓扑、算法、争用、归约开销与慢 rank 都会改变耗时。

### 误解八：GPU 越多，训练必然越快

强扩展时，每个 rank 的计算量下降，而部分 collective 的总字节数并不同比下降，延迟轮数还可能增加。最终会进入通信主导区间。

### 误解九：Barrier 能修复所有同步 bug

Barrier 只能让控制流会合，无法修复不匹配的 P2P、不同 collective 顺序或错误的 stream 依赖。

### 误解十：所有通信都应该使用 WORLD group

混合并行中的 DP、TP、PP、EP 各有独立语义和 group。使用错误 group 可能既慢又错，甚至直接 hang。

## 18. 用六道题检查自己是否真的懂了

### 问题一

4 个 rank 各持有模型参数的四分之一，现在每个 rank 都要运行一个需要完整参数的普通 Linear，应使用什么？

答案：AllGather。它把参数分片拼成每个 rank 都可见的完整参数，不需要归约。

### 问题二

4 个 rank 各自算出完整长度的局部梯度，但 optimizer 只在每个 rank 上更新四分之一参数，应使用什么？

答案：ReduceScatter。它聚合所有局部梯度，并只把与本地参数分片对应的结果留给该 rank。

### 问题三

为什么 DDP 不能只用 Reduce 把梯度送到 rank 0？

答案：普通 DDP 的每个 rank 都持有并更新完整模型，每个副本都需要相同的全局梯度；仅 root 有结果不够。可以使用 AllReduce，或 Reduce 后再 Broadcast，但后者只是另一种实现思路。

### 问题四

MoE router 为什么不适合用 AllGather 分发 token？

答案：不同 token 的目标专家不同。AllGather 会让所有 rank 获得全部 token，搬运大量无用数据；AllToAll 可以只把每个 token 路由到需要它的目标 rank。

### 问题五

Ring AllReduce 中 $M$ 是完整 tensor 大小时，为什么每 rank 发送量接近 $2M$ 而不是随 $p$ 变成 $pM$？

答案：tensor 被切成 $p$ 片。每个阶段有 $p-1$ 轮，每轮只发送 $M/p$；ReduceScatter 和 AllGather 两阶段合计 $2(p-1)M/p$。

### 问题六

为什么 `async_op=True` 后 profiler 仍可能看不到 overlap？

答案：后续计算可能立即依赖通信结果，也可能存在 stream 同步、buffer 冲突或硬件资源竞争。异步提交只是实现 overlap 的必要条件之一。

## 20. 一句话总结

> **通信原语本质上是 tensor 布局的变换契约：看清通信前数据在哪里、通信后谁需要完整值或分片、是否需要归约，就能从 Send/Recv、Broadcast、AllGather、ReduceScatter、AllReduce 和 AllToAll 中选出正确工具；再结合消息大小、通信组和物理拓扑，才进入真正的性能优化。**
