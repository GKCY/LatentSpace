# Training–Inference Mismatch：主要原因与应对方法

LLM 强化学习通常用推理引擎生成 rollout，再用训练引擎重算 token 概率、计算 loss 和梯度。即使两端加载同一份权重，对同一个前缀、同一个 token，也可能算出不同的概率。这就是本文关注的 **Training–Inference Mismatch（TIM，训推不一致）**。

模型的实际输出还取决于算子实现、计算精度、batch 形状、缓存和并行方式。权重相同，只对齐了其中一个条件。本文重点讨论这些同权重下的执行差异；参数陈旧、采样概率口径等问题会在后面单独说明。

## 1. 为什么 TIM 会影响 RL

固定同一个前缀和目标 token，先考虑两端使用同一正温度、且不做 top-p/top-k 等额外采样处理的情形。把生成数据的 rollout 概率记作 $\mu$，训练引擎用同一份旧权重重算的概率记作 $q$，当前训练概率记作 $p_\theta$，则：

$$
\frac{p_\theta}{\mu}
=\underbrace{\frac{p_\theta}{q}}_{\text{训练策略的更新}}
\cdot\underbrace{\frac{q}{\mu}}_{\text{同权重下的训推差异}}.
$$

在尚未更新参数、且训练侧前向可复现时，$p_\theta/q=1$，但 $q/\mu$ 未必等于 1。数据由 $\mu$ 采出，如果训练把它当作 $q$ 的样本，就会引入额外的 off-policy 偏差。使用 trainer 重算的旧概率作为 PPO 分母时，初始 PPO ratio 甚至可能等于 1，却没有检查到 rollout 与 trainer 的差异。[verl 的 rollout correction 说明](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html#overview)区分了这几个策略及相应的损失形式。

这也解释了为什么“生成的文字一样”不足以证明一致：RL 更新使用的是概率。假设某个 token 的 rollout 概率为 $10^{-6}$，训练侧为 $10^{-4}$，绝对差很小，概率比却达到 100。这样的尾部差异可能影响重要性权重和梯度贡献；是否导致某次训练退化，还需要对照实验确认。

## 2. TIM 的主要原因

### 2.1 算子实现、精度与量化不同

训练侧需要整段前向和反向传播，推理侧围绕生成吞吐、显存占用和延迟优化，因此两端常使用不同的 attention、RMSNorm、FFN 和 softmax 实现。即使数学公式相同，融合算子与分步计算也可能在不同位置做舍入，累加顺序和中间值精度也可能不同。

只核对模型的 dtype 不够。权重存储、乘法、累加、算子输出、KV Cache 和 logprob 各自都可能使用不同精度。例如，rollout 使用 FP8 或量化权重，trainer 使用 BF16；或者两端都标为 BF16，但一端保留 FP32 中间值，另一端提前转回 BF16，都可能造成差异。

提高关键算子的精度可以减小部分误差，但不能保证两端一致。把已经算出的低精度 logits 转成 FP32，也无法恢复前面计算中丢失的信息。相关数值行为可参考 [PyTorch 数值精度说明](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html)。

### 2.2 Dynamic batching 与 prefill/decode 改变了数值路径

浮点加法不满足结合律，同一组数换个归约顺序，结果就可能不同。推理引擎会随 batch 大小、序列长度和调度情况选择 kernel 配置，例如不同的分块方式、Split-K 或 Split-KV。于是，同一个请求与不同请求一起执行时，logits 也可能变化。

这也是 temperature 设为 0 仍可能出现不同输出的原因之一：它固定了 token 选择规则，却没有固定产生 logits 的计算过程。若两个候选的分数接近，微小变化就可能让 greedy 选择翻转。[Thinking Machines 的实验](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)具体分析了这种 batch 依赖。

跨训练、推理引擎时，还有逐 token decode 与整段 forward 的差别。rollout 往往复用 KV Cache，trainer 则一次重放完整序列；两者的矩阵形状、attention 分块和中间状态生成路径不同，即使可见前缀相同，概率也可能不完全一致。后来向推理服务重新请求整段 prompt logprobs，也未必能还原生成当时的 decode 概率。

因此需要区分三个目标：同一配置重复运行可复现、改变 batch 后结果不变，以及训练与推理两端一致。**推理侧具有 batch invariance，不能单独保证跨引擎一致。** [vLLM 与 TorchTitan 的一致性实验](https://vllm.ai/blog/2025-11-10-bitwise-consistent-train-inference)还逐一对齐了两端前向算子的实现。

### 2.3 并行切分与跨卡归约不同

训练和推理可能采用不同的张量并行（TP）、上下文并行（CP）或专家并行（EP）配置。即使逻辑计算相同，张量如何分片、在哪里求局部和、按什么顺序合并，以及通信使用什么精度，都可能改变最终结果。

例如，把一个完整矩阵乘拆到多张卡上，再合并部分结果，不一定与单卡计算得到逐位相同的输出。MoE 的专家输出即使已经对齐，dispatch/combine 阶段的排列恢复和加和路径也仍需核对。仅固定 batch 或使用同一套 kernel，不能据此推断不同并行配置之间也一致；这类问题需要单独做并行对照，见[训推一致性诊断](./训推一致性诊断：从概率偏差到根因定位.md)。

### 2.4 MoE 的离散路由放大了微小差异

MoE 的 router 会为每个 token、每个 MoE 层选择 Top-K 个 expert。当第 $K$ 名与第 $K+1$ 名的分数接近时，上游 hidden state 或 router 计算中的微小扰动，就可能改变入选的专家集合。

一旦选路翻转，token 会进入另一组 FFN 参数，变化就可能远大于最初的舍入误差，并继续影响后续层。rollout 生成时经过的专家，也可能与 trainer 重算概率、执行梯度更新时使用的专家不同。

这不要求 router 自带随机性；前面几类数值差异就足以触发离散选择变化。反过来，专家集合相同也不代表完整前向已经一致，混合权重、专家内部计算和输出合并仍可能不同。具体证据与路由对齐方法见 [R3 技术详解](<./R3：用Rollout Routing Replay解决MoE Agentic RL的训推不一致.md>)。

## 3. 还有哪些差异容易被一起记成 TIM

日志里的 rollout/trainer logprob gap 往往混合了多种来源。归因于浮点数值误差之前，需要确认两端比较的确实是同一个条件概率。

| 来源                   | 为什么会出现概率差异                                                                             | 对应处理                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 输入或模型语义没有对齐 | 重新分词、模板与截断、position IDs、attention mask、token 与 logprob 错位，或 dropout 等状态不同 | 保留实际 token IDs 和上下文，核对模型配置与评分位置；见[诊断专文](./训推一致性诊断：从概率偏差到根因定位.md)                |
| 采样概率口径不同       | temperature、top-p/top-k、重复惩罚等处理后的行为概率，不一定等于原始 softmax 概率                | 数值诊断时比较相同口径；算法校正时确认真实行为概率和支持集，见 [TIS 专文](<./TIS：用截断重要性采样缓解LLM RL训推不一致.md>) |
| 参数陈旧或版本混用     | 异步 rollout 使用旧权重，或者权重更新后仍沿用旧版本构建的 KV Cache                               | 记录生成版本，控制陈旧程度，保证权重切换与缓存处理一致；见[异步 RL 中的权重同步](../../../权重同步/主要RL框架重同步方案.md) |

这些问题可以与数值 TIM 同时存在，但处理方式不同。加快权重同步可以减小版本时滞，无法消除同权重下的算子差异；重要性加权也无法修复错位的 token 或错误的上下文。

## 4. 应对方法怎么选

方法可以从两处介入：让两端的实际计算更接近，或调整不一致样本对训练更新的贡献。下表保留选择方法所需的机制和边界，推导、实现与参数配置放在对应文章中。

| 方法                       | 主要解决什么                                                                  | 代价与边界                                               | 详细内容                                                                                                                                                                                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 对齐模型实现与数值路径     | 统一关键算子、精度和归约方式，减少 batch、prefill/decode 与并行路径引入的差异 | 需要在实际执行配置下验证；可能限制部分性能优化           | [诊断与算子定位](./训推一致性诊断：从概率偏差到根因定位.md)；[batch-invariant kernels](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)；[跨引擎一致性实例](https://vllm.ai/blog/2025-11-10-bitwise-consistent-train-inference) |
| R3：Rollout Routing Replay | 记录 rollout 实际选择的专家，在训练时重放，缩小离散路由差异                   | 增加路由记录与传输成本；不自动对齐混合权重或其他算子     | [R3 技术详解](<./R3：用Rollout Routing Replay解决MoE Agentic RL的训推不一致.md>)                                                                                                                                                                            |
| TIS：截断重要性采样        | 按目标概率与行为概率之比加权，并限制过大的权重                                | 截断引入偏差；具体比率与训练目标有关，不会让两端概率相等 | [TIS 技术详解](<./TIS：用截断重要性采样缓解LLM RL训推不一致.md>)                                                                                                                                                                                            |
| IcePop：双侧掩码校正       | 对区间内的概率比保留重要性加权，将区间外 token 的局部策略损失贡献置零         | 丢弃部分训练信号并引入偏差；需观察保留比例和梯度尺度     | [IcePop 技术详解](./IcePop：用双侧掩码校正稳定MoE强化学习.md)                                                                                                                                                                                               |

R3 可以与算法校正配合：先减少离散路由差异，再处理剩余概率偏差。TIS 与 IcePop 则是不同的权重处理规则，需要结合具体 loss 选择。PPO clipping 也不能替代这些工作，它的作用取决于使用哪个概率比，以及这个比率怎样进入代理目标。

实际处理时，先冻结权重，用生成时保存的 token 和 logprob 建立对照，再根据差异是否随 batch、精度、并行配置或路由变化来定位。除了均值，还应保留校正前的 logprob 差与概率比尾部，避免异常位置被过滤后，误以为两端已经一致。完整实验顺序、指标和验收方法见[训推一致性诊断：从概率偏差到根因定位](./训推一致性诊断：从概率偏差到根因定位.md)。
